## Naming

- **Go chaincode exported transaction functions are PascalCase methods on `*SmartContract`; internal helpers are lowerCamelCase package-level functions.** 100% consistent across both chaincodes, no exceptions found: `IssueCertificate`, `RevokeCertificate`, `GetCertificate`, `VerifyCertificate`, `GetCertificatesByInstitution` (chaincode/certificate-cc/issuecertificate.go, revokecertificate.go, queries.go) vs. `getCertificate`, `putCertificate`, `computeCertificateHash`, `certificateKey` (chaincode/certificate-cc/certificate.go); same split in chaincode/institution-cc/governance.go (`RegisterInstitution`, `ProposeNewMember`, `CastVote` vs. `getInstitution`, `putInstitution`, `txTimestamp`, `isFoundingInstitution`).
- **Go struct fields are PascalCase with an explicit `json:"camelCase"` tag** — every field in every model, no exceptions found: `chaincode/certificate-cc/model.go` (`Certificate`, `VerificationResult`), `chaincode/institution-cc/model.go` (`Institution`, `MembershipProposal`, `Vote`).
- **NestJS services and controllers are nouns suffixed `Service`/`Controller`; their methods are verb-first camelCase.** 100% of the 5 backend classes read follow this: `CertificatesService.issueCertificate/getCertificate/verifyCertificate/revokeCertificate/getCertificatesByInstitution` (backend/src/certificates/certificates.service.ts), `InstitutionsService.getInstitution/getAllInstitutions` (backend/src/institutions/institutions.service.ts), `FabricGatewayService.getInstitutionContract/getCertificateContract` (backend/src/fabric-gateway/fabric-gateway.service.ts).
- **DTO field names mirror the Go JSON tags exactly, field-for-field** — e.g. `CertificateDto` (backend/src/certificates/dto/certificate.dto.ts) reproduces every field of Go's `Certificate` struct (`certificateId`, `consortiumNumber`, `issuerSequenceNumber`, `issuerId`, `docType`, etc.) with matching casing; comments in the DTO files say this explicitly ("Mirrors chaincode/certificate-cc/model.go's Certificate struct exactly").
- **Frontend filenames are kebab-case; exported React components inside them are PascalCase; server actions/lib functions are camelCase.** Consistent across all files read: `certificate-table.tsx` exports `CertificateTable`, `status-badge.tsx` → `StatusBadge`, `revoke-section.tsx` → `RevokeSection`; `frontend/src/actions/certificates.ts` exports `issueCertificateAction`, `revokeCertificateAction`; `frontend/src/lib/session.ts` exports `setSession`, `getSession`, `requireSession`.
- **Import quote style is a hard boundary, not a shared convention**: 19/19 backend `.ts` files use single-quoted import paths (e.g. `backend/src/app.module.ts`), while 32/36 frontend `.ts`/`.tsx` files use double-quoted import paths (e.g. `frontend/src/lib/backend.ts`); the remaining 4 frontend files have no `from` import statement to sample. Each side is internally 100% consistent — this is two separate tool defaults (backend has no Prettier/ESLint style config committed at all; frontend inherits `eslint-config-next`'s defaults), not an unresolved inconsistency within one codebase area.
- **Trailing newline at end of file: 100% consistent (55/55 `.ts`/`.tsx` files sampled across backend and frontend end with a newline).** No inconsistency found here.
- Ambiguity: no naming convention was found anywhere for the network/ Go module (`network/internal/config`, `network/internal/generate`, `network/cmd/blcgen`) beyond standard Go exported-vs-unexported casing — too small a sample (one config package, one generate package) to say whether it matches chaincode's method/helper split or is its own thing.
- **Doc-derived addition** *(source: doc-derived V1_PHASE_OVERVIEW.md, confidence: medium)*: Certificate and proposal IDs deliberately use Fabric's deterministic `ctx.GetStub().GetTxID()`, not a randomly-generated UUID — confirmed in code at `chaincode/certificate-cc/issuecertificate.go:153` (`CertificateID: ctx.GetStub().GetTxID()`) and `chaincode/institution-cc/governance.go:358` (`ProposalID: ctx.GetStub().GetTxID()`). `governance.go:353-356`'s own comment states the reason: a random UUID would differ per endorsing peer and break multi-org endorsement determinism. This is a documented, deliberate deviation from an original design document's literal "UUID" spec, not a silent one.

## Error handling

Three genuinely different error-handling models exist, one per layer — this is not an inconsistency to resolve, but each is worth stating precisely since they interact at the HTTP boundary:

- **Go chaincode (both certificate-cc and institution-cc): every error is a returned `fmt.Errorf("...: %v", err)` string, 100% of the time.** No custom error types, no error codes, no `errors.New` without formatting, no panics in normal control flow (only `main.go`'s `log.Panicf` on unrecoverable startup failure — chaincode/certificate-cc/main.go, chaincode/institution-cc/main.go — which is a separate, non-transactional path). Verified by reading every non-test `.go` file in both packages: chaincode/certificate-cc/{issuecertificate,revokecertificate,certificate,queries}.go, chaincode/institution-cc/{governance,queries}.go.
- **The Go-error-string-to-HTTP-status mapping is done by regex against the literal English text of those `fmt.Errorf` messages**, in `backend/src/common/filters/fabric-exception.filter.ts`. This is explicitly flagged in that file's own comment as "a FIRST DRAFT, not verified against live output yet... unavoidably heuristic." There is no structured error code on the Go side for the filter to key off instead — the coupling is real and is between chaincode's prose and the backend's regex table, not between two versioned contracts.
- **NestJS backend: only one place throws a Nest `HttpException` subclass** — `ApiKeyGuard` throws `UnauthorizedException` (backend/src/common/guards/api-key.guard.ts). Every other thrown error in backend/src (6 occurrences: `fabric-gateway.service.ts` ×2, `fabric-identity.util.ts` ×2, `env.validation.ts` ×2) throws a plain `Error`, used for "should never happen" invariant violations (uninitialized service, missing env var, malformed keystore) rather than expected request-time failures. Domain/business errors (certificate not found, not the issuer, already revoked, etc.) are never thrown by backend code directly — they arrive as `EndorseError`/`CommitError`/`GatewayError` from the `@hyperledger/fabric-gateway` SDK and are caught centrally by `FabricExceptionFilter`, not by try/catch in individual services. `certificates.service.ts` and `institutions.service.ts` have zero try/catch blocks.
- **network/internal/config uses a different Go error pattern than chaincode: accumulate-all-and-join, not fail-fast-on-first.** `Validate()` in network/internal/config/validate.go collects every problem into `[]error` and returns `errors.Join(errs...)`, so one call reports all configuration problems at once. This is a deliberate difference for a validation-time UX (report everything wrong with network.yaml at once) versus chaincode's transaction functions (return the first error immediately, since a transaction either fully succeeds or fully fails).
- **Frontend: a single custom `BackendError` class** (`extends Error`, carries an HTTP `status`) wraps every non-2xx response from the backend — `frontend/src/lib/backend.ts`. Server actions (`frontend/src/actions/certificates.ts`, `frontend/src/actions/auth.ts`) catch `BackendError` specifically and turn it into a plain `{ error: string }` state object for the UI via `useActionState`-style state returns; any other thrown error is deliberately re-thrown (`throw error;`), not swallowed.
- **The same Go `fmt.Errorf` prose gets re-matched a second time on the frontend**, in `frontend/src/lib/error-messages.ts`'s `humanizeBackendError`, using its own separate regex table against the same message strings the backend's exception filter already parsed once. So a chaincode error message is string-matched twice, independently, at two different layers, with two different regex tables that must be kept in sync by hand.
- Ambiguity: whether `FabricExceptionFilter`'s status-code mapping has ever been checked against real Fabric Gateway output is explicitly unresolved in the filter's own comment — treat that mapping as provisional, not verified.

## API design

- **REST-ish, resource-based routes, no versioning prefix anywhere** (no `/v1`, no `Accept`-header versioning) — `backend/src/certificates/certificates.controller.ts` mounts at `certificates` (`POST /certificates`, `GET /certificates/:certificateId`, `GET /certificates/:certificateId/verification`, `POST /certificates/:certificateId/revoke`); `backend/src/institutions/institutions.controller.ts` mounts at `institutions` (`GET /institutions`, `GET /institutions/:institutionId`, `GET /institutions/:institutionId/certificates`).
- **Status codes are set explicitly per-route via decorators, not left to Nest's defaults, when the default would be wrong**: `revokeCertificate` overrides Nest's default 201-for-POST down to `200 OK` via `@HttpCode(HttpStatus.OK)` (certificates.controller.ts) because revoke mutates an existing resource rather than creating one; `issueCertificate` is left at Nest's default 201 for a `POST` that creates a certificate.
- **No response envelope for success responses** — controllers return the DTO (or array of DTOs) directly; there is no `{ data: ..., meta: ... }` wrapper. Error responses DO have a consistent shape, but only for the one error path the codebase controls: `FabricExceptionFilter` always emits `{ statusCode, error, message }` (fabric-exception.filter.ts). Validation errors from `ValidationPipe` (main.ts, global `whitelist: true, transform: true`) use Nest's own default validation-error shape instead, which is a different shape from the Fabric-error shape above — two error envelopes exist, not one, depending on which layer rejected the request.
- **Swagger/OpenAPI is used consistently**: every controller method read has `@ApiOperation` + `@ApiResponse` (and `@ApiParam` where there's a path param) — 100% of the 7 endpoints across both controllers. `main.ts` serves the generated doc at `/api`.
- **Auth is a single shared-secret bearer token, applied globally, with no per-route opt-out found**: `app.useGlobalGuards(app.get(ApiKeyGuard))` in main.ts checks `Authorization: Bearer <API_KEY>` against one env var; every route in both controllers is covered, there is no `@Public()`-style decorator anywhere to exempt a route.
- **No pagination anywhere** — `getAllInstitutions` and `getCertificatesByInstitution` both return the full unpaginated array (institutions.service.ts, certificates.service.ts); there is no `limit`/`offset`/cursor parameter on any GET route.
- Ambiguity: whether the two different error-envelope shapes (Fabric-filter JSON vs. Nest's default `ValidationPipe` shape) is an intentional two-tier design or simply never unified is not stated anywhere in code or comments — flagged, not resolved.

## Code review expectations

Based only on patterns actually observed to be followed consistently (not speculation):

- **Every exported Go function that can fail returns `(T, error)` and every call site checks the error immediately** — no ignored errors (`_`) were found on any fallible call across certificate-cc, institution-cc, or network/internal/config. A reviewer following the codebase's own established pattern would flag any new Go code that silently discards an error.
- **Every Go chaincode struct field intended to be sometimes-absent from contractapi's generated response schema carries both `json:"...,omitempty"` AND a `metadata:"...,optional"` tag together** — never just one. This is called out explicitly as a non-obvious, previously-hit gotcha in comments on `Certificate.Metadata`/`RevokedAt`/`RevokedReason` (chaincode/certificate-cc/model.go) and `Institution.ApprovedBy`/`MembershipProposal.ResolvedAt` (chaincode/institution-cc/model.go). A reviewer should flag any new optional chaincode struct field missing the `metadata:"...,optional"` half of the pair.
- **Every DTO file states which Go struct or function signature it mirrors, in a comment, before the class body** — 100% of the DTO files read do this (issue-certificate.dto.ts, certificate.dto.ts, revoke-certificate.dto.ts, verification-result.dto.ts, institution.dto.ts). A reviewer would reasonably flag a new DTO added without this cross-reference comment, since it's the only thing keeping the TS/Go shapes from silently drifting apart.
- **Chaincode never calls `time.Now()`** — every timestamp goes through a local `txTimestamp(ctx)` helper that reads `ctx.GetStub().GetTxTimestamp()`, with comments in both chaincodes explaining this is required for multi-peer endorsement determinism (chaincode/certificate-cc/issuecertificate.go, chaincode/institution-cc/governance.go). This is duplicated logic (near-identical `txTimestamp` function defined separately in each chaincode package, since they're independent Go modules) rather than a shared library — worth a reviewer noting as intentional duplication, not an oversight, given the module-independence comment in certificate.go's SmartContract doc.

## Do not touch without a senior human

| Area | Why | What breaks if you get it wrong |
|---|---|---|
| `network/scripts/network.sh` `cmd_wipe` (`down --wipe`, lines ~263-301) | Unconditionally wipes `network/crypto/*` via a throwaway container (`rm -rf /crypto/*`, line 294) and deletes `generated/`/`channel-artifacts/`, with no check for whether any org's MSP is already channel-committed. | Running this against a network with real, channel-committed org identities destroys the only copy of that crypto material; recovering means re-enrolling every org and rejoining the channel, and any org onboarded via governance vote would need to be re-proposed/re-voted since institution-cc's ledger state is untouched but the org's Fabric identity is gone. |
| `network/scripts/network.sh` `up` non-idempotency (documented in its own header, lines 11-20) | Stages 3 (crypto enrollment), 8 (orderer channel join), 9 (peer channel join) are explicitly NOT safely re-runnable — Fabric CA rejects re-registering an identity, Fabric rejects re-joining an already-joined channel. A partial failure requires a full `down --wipe` before retrying. | A senior human unaware of this will retry `up` after a partial failure and get confusing CA/channel-join errors, or worse, script past them and end up with inconsistent per-org crypto state. |
| `chaincode/institution-cc/governance.go` `requiredVotesToApprove` / vote-threshold logic (lines 17-24, 451-494) | Single source of truth for the consortium's approval math (majority today, described in comments as swappable to 66%). The majority-unreachable early-rejection logic (lines 478-493) is subtle: it was written specifically to avoid a stuck-vote bug at even voter counts (e.g. 2-of-2 splits). | An uninformed "simplification" here could silently reintroduce the stuck-vote bug (a proposal that can never resolve) or break the threshold formula for both existing and future organizations' membership votes. |
| `network/scripts/lib/crypto.sh` `bootstrap_org` (registrar vs Admin split, lines 118-215) | Deliberately enrolls the CA's own bootstrap identity into a separate, internal-only registrar home and never uses it as an org's channel Admin — mixing the two silently produces a cert with `OU=client` instead of `OU=admin`, which only fails much later at channel-join time, not at enrollment. | Collapsing this "for simplicity" reproduces a failure mode the comments say was already hit and diagnosed live; every future org bootstrap (via `org-add.sh`) depends on this split staying intact. |
| `chaincode/certificate-cc/issuecertificate.go` / `revokecertificate.go` authorization checks | `IssueCertificate` requires an *active* institution (line 128); `RevokeCertificate` deliberately does NOT re-check active status, only exact issuer-MSP match (lines 36-38 in revokecertificate.go, with an explicit comment on why this asymmetry is intentional). | Changing either check without understanding the asymmetry either lets a suspended/inactive institution issue new certificates, or stops a legitimately-departed institution from revoking its own historical bad certificates. |
| `crypto/ca-servers/<org>/` for any org already channel-committed (`founding`/`member`, or `pending` past `org-add.sh` stage 3) — see `context/decisions/ADR-0001-never-delete-committed-ca-server-crypto.md` | This directory holds the CA's own root keypair, generated on first startup. Once an org's MSP is injected into the channel, that specific root cert is permanently pinned into channel trust — there is no code-level guard stopping a "targeted cleanup" from deleting it anyway. | A partial/scoped deletion here (not a full network wipe) destroys the root keypair itself, not just the registered-identity conflict it was meant to fix — the org's channel-trusted identity becomes permanently unrecoverable, requiring a full `network.sh down --wipe` and complete redo (this has already happened once live, per ADR-0001). |

## Doc-derived additions

> *(source: doc-derived V1_PHASE_OVERVIEW.md, confidence: medium — extracted
> during the 2026-07-30 doc-archaeology pass, confirmed against code below)*

- **The `requiredVotesToApprove` majority-unreachable rejection (see "Do not touch" row above) was chosen over two other alternatives that were explicitly considered and rejected, per the code's own comment** (`chaincode/institution-cc/governance.go`, the `else` branch of `CastVote`, ~lines 478-493): (1) waiting for 100% voter participation before ever resolving a proposal — rejected because it can stall forever (the comment cites the project's first real 2-voter vote as the case that exposed this); (2) mirroring the approval threshold directly against `VotesAgainst` — rejected because it has "a real stuck-vote bug at even N, including N=2" (a 1-yes/1-no split with 2 total voters never resolves). The chosen approach — reject as soon as `maxPossibleYes < requiredVotesToApprove(...)` — is directly exercised by `TestCastVote_N6_CloseRace_FinalYesApproves` and `TestCastVote_N6_CloseRace_FinalNoRejects` (`chaincode/institution-cc/castvote_test.go`), confirming the "traced 6-voter close-race scenario" the source doc describes.

## Performance / security watch list

- `chaincode/certificate-cc/queries.go` `GetCertificatesByInstitution` (lines 32-57) runs an unbounded CouchDB rich query (`docType`+`issuerId`, no CouchDB index shipped with the chaincode package, per its own comment) and sorts the full result set in Go memory — no pagination anywhere in the call chain (`backend/src/certificates/certificates.service.ts` lines 46-56 and `backend/src/institutions/institutions.controller.ts` lines 31-39 both return the full array). An institution with a large certificate history will pay an increasing full-scan + full-sort cost on every list view.
- A single shared `API_KEY` per backend instance (`backend/src/common/guards/api-key.guard.ts`) is the only HTTP auth boundary; there is no per-user attribution once inside an institution, no rate limiting on the guard itself, and no key-rotation mechanism — a leaked key gives full read/write access to that org's chaincode identity indefinitely until someone manually regenerates and redistributes it.
- CA, peer, and CouchDB ports are all published with the bare `"hostport:containerport"` docker-compose syntax (e.g. `network/templates/docker-compose-net.yaml.tmpl` lines 61, 76; `docker-compose-ca.yaml.tmpl` lines 14, 29), which Docker binds to `0.0.0.0` by default — every one of these services is reachable from any network interface on the host, not just `localhost`, despite connection profiles and local tooling assuming `localhost`-only access.
- `chaincode/institution-cc/governance.go`'s `countActiveInstitutions` and `approvingVoters` (lines 257-306) each do a full CouchDB rich-query scan on every `ProposeNewMember`/`CastVote` call; fine at today's consortium size (single digits) but worth revisiting if membership grows meaningfully.
- `network/scripts/org-add.sh` is 928 lines with 7 ordered stages, several of which shell out to `python3 -c "..."` inline for YAML parsing and JSON validation (e.g. lines 130-141) — functionally correct per its own extensive commentary, but the size and inline-scripting style make it a high-review-cost file for future onboarding-flow changes.
- No automated test harness was found for the bash scripts under `network/scripts/` (only Go unit tests exist, under `chaincode/*/**_test.go`) — all onboarding/lifecycle correctness currently rests on manual runs plus the in-script comments describing prior live failures.
